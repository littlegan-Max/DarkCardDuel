## 0. 本阶段定位与前置

- **节点**：节点场景组织 → GDScript 系统编码 → 信号解耦 → 资源与存档 → 平台接入
- **准出**：规则内核 headless 全用例通过；战斗场景可完成一局完整对局；存读档与回放可复现同一结果
- **不在本阶段**：帧率调优、真机适配、商店打包（阶段三/四）

**这一阶段最大的技术风险不是"写不出来"，而是"规则写散了"**：50 张牌 × 每张牌一个"可被列" × 10 步结算顺序，如果按"一张牌一个 if"写，第 20 张牌就会开始互相打补丁。本方案的核心就是**把规则从代码里赶出去，赶进数据表和一条固定管线**。

## 1. 五条架构原则

| # | 原则 | 具体做法 | 违反的后果 |
|---|---|---|---|
| P1 | **规则内核与表现分离** | 规则层是纯 `RefCounted`，不继承 `Node`、不碰 `Tween`、不读输入、不发信号给 UI | 规则无法 headless 测试，AI 与回放要重写一套 |
| P2 | **数据驱动** | 50 张牌写成 JSON，效果用 op 码表表达；新增牌不改代码 | 每张牌一个 `match`，第 30 张牌开始不可维护 |
| P3 | **确定性** | 定点整数、固定结算顺序、无随机（或随机全部来自种子） | 回放对不上、联机不同步、BUG 无法复现 |
| P4 | **事件流驱动表现** | 结算产出 `RuleEvent[]`，演出层**回放事件**，不重算规则 | UI 与规则两套判定，必然不一致 |
| P5 | **服务端权威** | 客户端只提交"我出哪张"，不本地判定对方 | 双盲同翻被改包/透视 |

## 3. 场景树

### 3.1 启动与外壳

```
Boot.tscn
└─ Boot (Node)
   ├─ BootLoader (Node)          # 加载 ContentDB、检查更新、初始化存档
   └─ Splash (CanvasLayer)

AppShell.tscn                    # 常驻，切换 Screen
└─ AppShell (Node)
   ├─ Router (Node)              # 唯一负责场景切换的节点
   ├─ ScreenHost (Control)       # 同一时刻只挂 1 个 Screen
   ├─ OverlayHost (CanvasLayer)  # 弹窗 / Toast / 断线遮罩（layer=10）
   └─ FadeLayer (CanvasLayer)    # 转场（layer=20）
```

**铁律**：除 `Router` 外，任何节点不得调用 `change_scene_to_file`。场景切换只走 `Router.go(screen_id, payload)`，否则返回键、转场动画、内存释放会互相打架。

```
   │  ├─ EnemyPanel (Control)        # 血/运/盾/冷却/dot

   │  ├─ SelfPanel (Control)
   │  └─ ComboBar (Control)          # 连招进度 x/3
   ├─ HandTray (Control)

   │  ├─ SearchBox (LineEdit)
   │  ├─ CardScroll (ScrollContainer)
   │  │  └─ CardPool (Control)       # ★ 只放 12 个 CardChip，循环复用
   │  └─ ConfirmBar (Control)        # 确认出牌 / 撤回
   ├─ RevealLog (CanvasLayer)        # 结算日志（对应 10 步）
   └─ BattleAudio (Node)
```

**为什么 `CardPool` 只有 12 个节点**：50 张牌若各建一个 `CardChip`（每个含 底色/卡面/费用/名称/角标 ≈ 5 个 CanvasItem），就是 250 个绘制项，滚动时全量 `_draw` 与布局重算会把中端机拖到 40fps 以下。做法：

- 数据层只有 50 条 `Dictionary`；
- 视图层 12 个 `CardChip` 复用，按 `scroll_offset` 计算可见区间并 `bind(card_id)`；
- 卡面用 `AtlasTexture` 从 2048² 图集取，避免 50 张独立纹理；
- 只有"选中/详情"才实例化独立浮层。

## 4. 规则内核设计

### 4.1 回合状态机（TurnDirector）

```
IDLE → WAIT_INPUT → LOCKED → REVEALING → RESOLVING → SETTLE → (WAIT_INPUT | GAME_OVER)
```

| 状态 | 允许的操作 | 超时行为 |
|---|---|---|
| WAIT_INPUT | 选牌/换牌/看详情/查日志 | 进入 5s 加时，仍无则自动出"运" |
| LOCKED | 只能撤回（若双方未都锁定） | — |
| REVEALING / RESOLVING | 只能加速/跳过演出 | 自动播完 |
| SETTLE | 无 | 自动进下一回合 |

### 4.2 核心数据结构

```gdscript
# scripts/core/duel_state.gd
class_name DuelState
extends RefCounted

var turn_index: int = 0
var players: Array[PlayerState] = []       # 固定 2 个，下标 0/1
var history: Array[TurnRecord] = []        # 每回合出牌 + 事件流
var rng_seed: int = 0
var rule_version: String = "2.1"   # 2026-10-24 五条裁定并入后冻结

class PlayerState:
    var hp: int = 100                      # 定点：100 = 1.00 血
    var hp_max_ever: int = 100             # 净化用（A3）
    var yun: int = 0                       # 定点：10 = 1.0 运，允许 0.5（作者 2026-10-24：不要求整数）
    var shields: int = 0                   # 存储无上限（B8）
    var cooldowns: Dictionary = {}         # card_id -> 剩余回合
    var dots: Array[DotInstance] = []      # 偷袭 / C4
    var flags: Dictionary = {}             # banned_next_turn / fly_dragon_ready 等
    var played_last_turn: String = ""
```

**关键点**

- **双定点标尺**：血量 1 = 100（0.01 精度），运 1 = 10（0.1 精度，够表达葵花减半后的 0.5/1.5/2.5/3.5）。全工程禁用 `float` 做数值比较与结算。原因：作者已确认"全局数字都是小数"，葵花/元首会产生 0.5 级费用，毒药是 80% 比例伤害，浮点累加在 20 回合后会出现 `0.30000000000000004`，导致"看起来 0 血但没死"、回放哈希对不上。
- `hp_max_ever` 单独记，不能在 `hp` 上做 `max()`，因为加血可超过 1 且可被扣回。
- `shields` 是整数（意大利炮/核弹要 2 张），不是布尔。
- `cooldowns` 存"剩余回合数"而不是"上次使用回合"，避免回合索引改动时全表重算。

### 4.3 结算入口

```gdscript
# scripts/core/turn_resolver.gd
class_name TurnResolver
extends RefCounted

func resolve(state: DuelState, card_a: String, card_b: String) -> Array[RuleEvent]:
    var ctx := ResolutionContext.new(state, card_a, card_b)
    var ledger := HpLedger.new(state)
    var events: Array[RuleEvent] = []

    events += _phase_reveal(ctx)          # B4-1
    events += _phase_turtle(ctx)          # B4-2 龟派转化
    events += _phase_amulet(ctx)          # B4-3 护身符
    events += _phase_time_reverse(ctx)    # B4-4 扭转时空
    events += _phase_counter(ctx)         # B4-5 闪 → 可被列 → 吸
    events += _phase_resource(ctx)        # B4-6 运/加血/debuff/盾入库
    events += _phase_damage(ctx, ledger)  # B4-7 伤害互拼（dot 强制结算）
    events += _phase_shield_save(ctx, ledger)  # B4-8 盾保命
    var deaths := _phase_death(ctx)       # B4-9 死亡判定
    events += deaths.events

    if deaths.is_mutual_tie():
        # A2/C29 + 2026-10-24 裁定：同死只作废血量变化，其余照常
        ctx.clear_code_kills()            # 双方均被代码杀（如双方自杀）→ 死亡一并作废，对局继续
        ledger.rollback_hp_only()         # 血量回到回合开始（"不扣血"）
        events += [RuleEvent.damage_voided(ctx.turn_index)]

    events += _phase_settle(ctx)          # B4-10 连招/冷却/封牌落账
    state.history.append(TurnRecord.new(ctx, events))
    state.turn_index += 1
    return events
```

**为什么必须"先算完再回滚"**：A2 的同死是"事后判定"，不是"事前拦截"。如果写成"预判双方会不会同死"，就要在每一步之前模拟剩余步骤，复杂度爆炸且必错。正确做法是**完整结算 + 血量事务回滚**，其余账目（运、费用、连招、冷却、dot）不动（C29）。

### 4.4 血量事务（HpLedger）

```gdscript
class_name HpLedger
extends RefCounted

var _state: DuelState
var _snapshot: Array[int] = []       # 回合开始血量
var _entries: Array[Dictionary] = [] # {player, delta, cause, source_card}

func begin() -> void:
    _snapshot = [_state.players[0].hp, _state.players[1].hp]

func apply(player: int, delta: int, cause: String) -> void:
    _state.players[player].hp += delta
    if delta > 0:
        _state.players[player].hp_max_ever = maxi(
            _state.players[player].hp_max_ever, _state.players[player].hp)
    _entries.append({"player": player, "delta": delta, "cause": cause})

func rollback_hp_only() -> void:
    for i in 2:
        _state.players[i].hp = _snapshot[i]
    # hp_max_ever 不回滚：本局"达到过的最高血"是既成事实（A3 语义）

func commit() -> void:
    _entries.clear()
```

> 设计取舍：`hp_max_ever` 在回滚时**不恢复**。理由：A3 说的是"本局达到过的最高血量"，同死作废的是"该回合伤害"，不是"该回合加血"（C29 明确加血照常执行）。如果连加血也回滚，净化会回退到一个从未存在过的血量。**此条需作者确认，标为 Q3。**

### 4.5 反制判定（B1 的唯一实现）

```gdscript
func _is_countered(attacker_card: SkillDef, defender_card: String, ctx) -> bool:
    if defender_card == "shan":
        return attacker_card.id != "shou_qiang"        # 手枪不可被闪
    if defender_card == "jue_xing_zhong_fang":
        return attacker_card.targets_opponent            # 只挡"对自己使用"
    return defender_card in attacker_card.countered_by    # 可被列是唯一依据
```

**禁止**写 `if card.cost < defender.cost` 这类"数值大小"判断。B1 明确"可被列就是权威，与伤害数值无关"。

### 4.6 四类"非普通伤害"的时序（批 2 落地）

| 机制 | 落点 | 关键约束 |
|---|---|---|
| dot（偷袭） | **伤害阶段**（第 7 步） | 不经过反制/无效化；**使用回合不跳**，此后每回合跳一次，共 `turns` 次。用 `born == turn` 跳过使用回合。桃桃在资源阶段清空 `dots`，先于当回合跳伤 |
| 酒 | **伤害阶段之前**判定 | `immune_le` 只在"本回合"有效，SETTLE 阶段重置为 -1；按 `abs(amount) <= immune_le` 判，dot 单跳同样适用 |
| 运挡为抵消（超掐/手枪） | **反制阶段**置标记，**资源阶段**跳过运的 `YUN_ADD` | 只对 `yun_block="consume"` 的攻方生效；"运挡不消耗运"是默认，抵消是例外 |
| 三棱镜 | **资源阶段**计算 k，伤害阶段落地 | k 只数"本回合出的牌本身"（含被挡/被吸），不数运增减效果；`dmg = 40 + 30k`，**为负时是给对方加血** |

> 这四条都不能靠"给某张牌写 if"实现，否则批 3 的 C4、判负、净化会重复踩坑。全部走 op + 牌级字段。

## 5. 技能数据化

### 5.1 JSON 结构

```json
{
  "id": "xiao_biao",
  "name_key": "card.xiao_biao.name",
  "cost": 1,
  "cost_kind": "fixed",
  "countered_by": ["zhong_fang", "xi"],
  "tags": ["attack"],
  "targets_opponent": true,
  "ops": [
    { "op": "DMG", "amount": 100 }
  ],
  "notes_key": "card.xiao_biao.note"
}
```

```json
{
  "id": "ding_hai_shen_zhen",
  "cost": 4,
  "countered_by": ["kai_sa", "nai_bao", "shou_qiang", "nao_gua_beng"],
  "targets_opponent": true,
  "ops": [
    { "op": "DMG", "amount": 160, "on_countered": "skip" },
    { "op": "HEAL_SELF", "amount": 60, "on_countered": "still" }
  ]
}
```

> `on_countered` 字段解决 C32"被防仍加血"这类例外：**默认被抵消则整张牌的效果不结算，例外必须显式声明**。这比在代码里给某张牌开洞可控得多。

> `cost_kind` 取值：`fixed`（固定费用）/ `combo`（连招门，费用随牌面）/ `all_in`（核弹：名义 4，实付 `min(max(运,0),4)`，**合法性永不拦截**）。

**龟派的实现方式（唯一不写 50 个 if 的做法）**

`ResolutionContext.redirect[i]` 记录"牌 i 的效果归属者"，默认是 i。龟派阶段只做一件事：`redirect[对方] = 龟派者`。之后所有阶段统一读 `owner_of(i)` 与 `target_of(i)`：

- `target = "enemy"` → 目标 = `1 - owner`（攻击牌反打原主）
- `target = "self"` → 目标 = `owner`（自增益转给龟派者）
- `target = "global"` → 无差

于是"自杀被龟派 → 龟派者死"（`target=self`）与"小镖被龟派 → 原主挨打"（`target=enemy`）自动成立，不需要为任何一张牌写特例。

### 5.3 数据校验（CI 必过）

`tools/validate_cards.gd` 检查：

1. `id` 唯一、文件名与 id 一致
2. `countered_by` 里每个 id 都存在（防拼写错）
3. `ops` 里每个 op 都在码表内，参数齐全
4. `cost` 为非负、0.5 步进
5. 每张牌必须有 `name_key`、`notes_key`，i18n 表里必须有对应条目
6. 50 张全在、无孤儿文件

## 6. 龟派转化（全项目最复杂的一段）

### 6.1 为什么不能"逐牌写"

龟派要处理 50 张牌 × 目标方向 × 数值翻倍 × 不翻倍例外（C34）。若逐牌 `match`，工作量 50 份且每加一张新牌都要回来改。

### 6.2 用"目标语义 + 数值域"表达

每张牌的 op 只声明**目标语义**（`SELF` / `OPPONENT`），转化时统一重写：

```gdscript
# Rule: 转化后的目标重写
# A 出牌，B 出龟派
# 原 SELF（A 对自己）→ 变成 B 对自己
# 原 OPPONENT（A 对 B）→ 变成 B 对 A
func convert_ops(ops: Array, multiplier: int) -> Array:
    var out := []
    for op in ops:
        var c := op.duplicate()
        c.target = ("SELF" if op.target == "OPPONENT" else "OPPONENT")
        if c.has("amount") and _is_numeric_domain(op.op):
            c.amount = op.amount * multiplier      # 神之龟派 ×2
        out.append(c)
    return out

func _is_numeric_domain(op_name: String) -> bool:
    # 只翻倍 ±血 / ±运；不翻倍回合数、百分比、费用、次数（C34）
    return op_name in ["DMG", "TRUE_DMG", "HEAL", "HEAL_SELF", "YUN_ADD"]
```

### 6.3 归属账本（C22 的关键）

龟派者有"三不算"：不付费、不算出过、不占冷却。但**原使用者照样算**。所以每回合要维护两份账：

| 账 | 龟派者 B | 原使用者 A | 用途 |
|---|---|---|---|
| `paid_cost` | 0 | 原牌费用 | 吸的结算、护身符阈值 |
| `counts_as_played` | 只记 `gui_pai` | 记原牌 | 冷却、连招、三棱镜 k |
| `effects_resolved` | 转化后的 op | 全部无效（自杀除外） | 实际效果 |

> 三棱镜 k 的统计口径：只数"出过运/强化运这张牌本身的人"，按 `counts_as_played` 数，所以龟派者用龟派借来的运**不计入 k**（C22 的直接推论）。这条必须写成用例。

### 6.4 特殊分支（显式白名单，不放进通用逻辑）

| 牌 | 结果 | 实现 |
|---|---|---|
| 自杀 | B 死，A 活 | `CODE_KILL` 的 target 转化后指向 B，且不受"被转化牌无效"影响 |
| 扭转时空 | 本回合全体无效（与不转化同效） | `NEGATE_ALL` 幂等 |
| 龟派 / 神之龟派 | 双方均不生效 | 在 `_phase_turtle` 入口判双方都出龟派 → 直接 return |
| 战术核弹 | 免费，-2.2 | `paid_cost = 0`，无视其"全押 4 费"（C31 龟派一律免费） |
| 葵花宝典 | B 获得"自己后续费用减半"，A 的葵作废 | `COST_MULT` 目标重写后挂到 B；A 的 buff 撤销（旧适配表的"A 消耗×50%"是旧语义残留，已废止） |
| 定海神针 | A -1.6，B +0.6 | 通用目标重写即可，无需特判 |

## 7. 状态账本细则

| 机制 | 数据结构 | 易错点 |
|---|---|---|
| 冷却 | `cooldowns[card_id] = 剩余回合` | 吸与超级吸**共享池**（B7）：用 `pool_id = "xi_pool"` 而非 card_id |
| 不可连用 | 同上，CD=1 | 被挡/被吸仍要进冷却（B2） |
| 连招 | `history` 尾部倒推匹配 | 被挡也算（C20）；中断清空（A4）；核弹用后清空连招运 |
| 降飞特权 | `flags["fly_dragon_ready"] = true` | "运挡后还在"是一次性许可，用后清除 |
| 封牌 | `flags["banned_next_turn"]` | 被中防/小镖挡下则不封（B15） |
| 盾 | `shields: int` | 2 张才挡的牌，不足 2 张**不消耗**（B8/C38） |
| dot | `dots: [{tick, remain, source}]` | 可叠加，各自计时（C15）；桃桃可永久解除（C17） |
| 净化 | CD 2，`hp_max_ever` | 只作用自己（C12）；2 人局"被喂桃桃"无效（待确认项） |
| 比心 | `YUN_CAP_MIN: -3` | 只限制**比心自己**造成的减运，其他减运无下限（C26） |
| 真伤 | `TRUE_DMG` 不受中防，但受闪/盾 | 酒的 ≤1 阈值按**该次攻击总伤害**判（B9） |
| 核弹费用 | `cost_kind="all_in"`，名义 4 | **出牌锁定瞬间**结算，实付 `min(max(运,0),4)`；合法性永不拦截；葵不作用；护身符按 4 判定 |
| 勾魂 | `steal = max(0, yun)` | 负运归零、不夺负值 |
| 盾价 | `flags.shield_bought_once` | 首次 4、之后永久 3；葵后 2 / 1.5 |
| 毒药 | `floor(hp * 80 / 100)` | 定点向下取整，避免 1.024 变 1.03 |

## 8. 网络方案

### 8.1 权威模型

| 模式 | 权威方 | 说明 |
|---|---|---|
| 单机 AI | 本地 | 规则内核本地跑，无网络 |
| 好友 P2P | 主机方 | 需 commit-reveal 防偷看 |
| 在线排位 | **服务端** | 客户端不持有对方选择，服务端结算 |

### 8.2 协议（回合制请求-响应）

| 消息 | 方向 | 字段 |
|---|---|---|
| `MatchJoin` | C→S | match_id, deck_version |
| `TurnSubmit` | C→S | turn, card_id, nonce |
| `TurnResult` | S→C | turn, events[], state_digest, deadline_ms |
| `StateSync` | S→C | turn, snapshot（重连用） |
| `MatchEnd` | S→C | winner, reason, replay_id |

**要点**

- 服务端收齐双方 `TurnSubmit` 后才 `resolve()`，结果下发**事件流**而非"最终血量"，客户端只做演出。这样客户端无法通过改包改变结果，也无法提前推断对方牌。
- `state_digest` = 关键状态哈希，客户端可比对，发现不一致立即 `StateSync`（防"看起来赢了其实没赢"）。
- 断线：服务端保留 30s；重连发 `StateSync` + 未播完的 `events`。

### 8.3 P2P 的 commit-reveal（仅好友对战）

1. A 发 `H = sha256(card_id + nonce + turn)`
2. B 发 `H'`
3. 双方收到对方 H 后才发 `card_id + nonce`
4. 校验 H，不一致判负

> 成本：多一个 RTT。**排位绝不用 P2P**，因为主机方可以看到对方 commit 后暴力枚举 50 张牌（50 次哈希即可），commit-reveal 对 50 选 1 的空间没有保密性。这一点必须在方案评审时讲清楚，避免"想省服务器"埋雷。

## 11.5 对手习惯模型（app 内置，持续学习）

### 目标

**只要 app 开着，就持续学习玩家（人类）的出招习惯**，并用它提高 AI 的应对质量。
这不是"读心"——模型只统计可观测的行为：出牌频次、情境偏好、套路度、攻防倾向、连招意图。

### 模块

| 模块 | 职责 | 依赖 |
|---|---|---|
| `scripts/ai/opponent_model.gd` | 纯逻辑：记录、倾向查询、置信度、序列化 | 无（RefCounted） |
| `scripts/ai/opponent_store.gd` | 持久化：读写 `user://opponent_model.json`，版本迁移、损坏兜底、备份 | OpponentModel |
| `scripts/ui/opponent_profile.gd` | 画像面板：把学到的倾向显示给玩家，支持一键清空 | OpponentModel + CardDB |
| `scenes/battle/battle_screen.gd` | 接线：每回合 observe；AI 选牌前算 habit/mix；局末与退出时落盘 | 上面三者 |

### 学习的五个维度

| 维度 | 记录内容 | 用途 |
|---|---|---|
| 全局牌频 | 每张牌被出的次数（带衰减） | 样本不足时的回退倾向 |
| 情境偏好 | `回合阶段｜血量区间｜运区间｜上一手性质` → 牌分布 | 主力信号：AI 在相似情境下预判玩家 |
| 套路度 | 连续出同一张牌的比例、最长连续次数 | 判断"可预判程度" |
| 攻防倾向 | 攻击/防御/资源/治疗占比 | 画像展示与策略微调 |
| 连招意图 | 铺垫前置的次数 vs 完成连招的次数 | 识别玩家在铺龟派/葵花这类组合 |

### 上下文键为什么做得很粗

`回合阶段｜血量区间｜运区间｜上一手性质` 只有 4 维，每维 3~4 档 → 情境总数约 100 量级。
细分会让每个情境的样本太稀疏，**学不到东西**；太粗又失去针对性。这个粒度是权衡结果。

### 置信度与混入权重

`confidence = 超出均匀分布的幅度 × 样本量置信系数`，再乘上限 `MAX_MIX = 0.35`：

```
p_final = (1 - mix) * p_learned + mix * p_habit
```

样本不足（< 8 次）或倾向不明显时 mix 趋近 0 —— **不用噪声当信号**。

### 持久化与迁移（对应审计 P0-6）

| 项 | 做法 |
|---|---|
| 路径 | `user://opponent_model.json`（平台无关） |
| 版本 | `schema_version = 1`，`OpponentStore._migrate()` 负责 v0 → v1 |
| 写入 | 先写 `.tmp` 再替换，替换前把旧档转存 `.bak` |
