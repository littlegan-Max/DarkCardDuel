## 2. 四个角色

### 2.1 游戏设计总监（本角色）

| 项 | 内容 |
|---|---|
| 负责 | 玩法循环、机制规格、数值框架、平台规格、商业化选项、指标树、阶段编排 |
| 交付 | GDD、数值表、平台规格书、变更记录、阶段评审结论 |
| 不做 | 写 GDScript、调帧率、出测试报告、代办版号 |
| 技能模块 | `godot-game-gameplay-design`、`godot-game-economy-monetization` |
| 关键纪律 | 玩法可三句话复述；数值必须落在表里；不替用户拍板商业化 |

### 2.2 核心开发工程师

| 项 | 内容 |
|---|---|
| 负责 | 目录/场景组织、规则内核、数据驱动、信号解耦、存档回放、网络接入、平台导出配置 |
| 交付 | 可运行工程、规则内核、50 卡数据表、接口说明、构建号 |
| 不做 | 决定玩法、改牌面数值、宣布性能达标 |
| 技能模块 | `godot-game-core-development`、`godot-game-version-upgrade` |
| 关键纪律 | 规则内核不碰 Node；事件流驱动演出；血量定点整数 |

### 2.3 性能调试工程师

| 项 | 内容 |
|---|---|
| 负责 | 帧预算、真机基线、绘制/节点/内存优化、降级策略、优化前后对比 |
| 交付 | 性能报告、优化清单、真机矩阵结论 |
| 不做 | 改玩法、改规则、替测试签字 |
| 技能模块 | `godot-game-perf-debug` |
| 关键纪律 | 只看 P95 不看平均；任何 > 50ms 单帧算缺陷；不接受"低端机就这样" |

### 2.4 测试发布工程师

| 项 | 内容 |
|---|---|
| 负责 | 测试策略、规则用例验收、真机验收、导出模板、AAB/ipa、灰度、线上问题闭环 |
| 交付 | 测试报告、验收清单、发布包、发布记录 |
| 不做 | 改代码、改数值、绕过商店合规 |
| 技能模块 | `godot-game-qa-release` |
| 关键纪律 | 每个线上问题必须有责任人与修复轮次，不静默关闭 |

### 2.5 角色合并的现实规则

若团队只有 2–3 人：

- 性能可由核心开发兼任，但**性能报告必须独立成文**（自己给自己打分不算验收）。
- 测试发布**不可由开发者兼任**，最低要求是"独立的人跑一遍 + 真实设备"。
- 设计总监不可兼任测试（会对自己写的规则有确认偏误）。

## 3. RACI

| 活动 | 设计总监 | 核心开发 | 性能调试 | 测试发布 |
|---|---|---|---|---|
| GDD / 数值框架 | **A/R** | C | I | C |
| 规则口径裁定 | **A/R** | C | I | C |
| 场景/节点组织 | C | **A/R** | C | I |
| 规则内核编码 | I | **A/R** | I | C |
| 50 卡数据表 | **R** | **A** | I | C |
| 性能预算 | C | C | **A/R** | I |
| 真机基线采集 | I | C | **A/R** | C |
| 测试用例设计 | C | C | I | **A/R** |
| 导出/发布 | I | C | C | **A/R** |
| 线上问题闭环 | A | R | R | **R** |
| 版本升级评估 | A | **R** | C | C |

> A=批准，R=执行，C=咨询，I=知会。**每个活动只能有一个 A**。

> 周期为**相对周**，假设 3–4 人全职。团队规模未知（见 01 文件待补 6），此处只给相对顺序与依赖，不承诺绝对日期。

| 里程碑 | 相对周 | 交付 | 门禁 |
|---|---|---|---|
| M0 立项 | W0 | 本立项包 + 5 项决策拍板 | 待补清单清零 |

## 7. 规则变更控制（本项目最重要的一条流程）

规则文档有 A/B/C 三级裁定、50 张牌、上百条互动。**任何口头变更都会在两周后变成两个版本的实现**。

### 7.1 RFC 模板

```markdown
# RFC-0007 葵花宝典作用对象与倍率

- 提出人 / 日期：设计总监 / 2026-10-24
- 现状：技能表与 B10 写"对方整局所有技能消耗×50%"，第八部分备注"暂按 ×1.5 执行"（方向与倍率双重矛盾）
- 裁定：**出招者自己**后续费用减半（×0.5），对可变 cost 无效
- 影响裁定：B10、C42、C43
- 影响卡牌：葵花宝典、护身符（2~3 费阈值）、意大利炮、六神/六飞、盾
- 影响代码：`COST_MULT` 的 `scope=self`、`ratio=0.5`
- 影响用例：`test_c42_kui_self_cost_half`、`test_c43_*`
- 回放兼容：是（v2.0 老回放按旧规则包重跑）
- 生效版本：rules v2.1
- 状态：**已批准（作者 2026-10-24），待回写**
```

### 7.2 冻结窗口

| 阶段 | 允许的变更 |
|---|---|
| M1 前 | 任意 |
| M1–M4 | 只接受"实现发现规则歧义"的澄清型 RFC |
| M4 后 | 只接受 P0（会导致对局结果错误）修正，且必须单独回归 |

### 7.3 每条变更的三件事

1. 规则文档版本 +0.1，保留旧版本目录（回放要用）
2. 对应测试用例同步增删
3. 在 GDD 的"变更记录"里留一行

## 8. 引擎版本策略

| 项 | 结论 |
|---|---|
| 当前锁定 | **Godot 4.7.2**（2026-08 维护版，核验 2026-10-24） |
| 4.8（预计 2026 Q4） | **不追**。上线前不升级，避免"升级夹带功能" |
| 升级触发条件 | 上线后一个完整赛季，且出现"必须新版才能修的安全/平台问题" |
| 升级三段式 | 评估（API 变更清单/插件兼容/导出模板）→ 迁移（单独分支）→ 回归（金样回放 + 三档真机） |
| 回滚点 | 升级分支必须保留上一版可出包状态 |

> 铁律：升级单独分支、单独回归、单独出包；升级中每处 API 变更都要落到迁移记录。
