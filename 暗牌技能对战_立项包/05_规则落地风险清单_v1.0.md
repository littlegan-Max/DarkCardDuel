## 1. 已裁定（作者 2026-10-24）

### Q1 葵花宝典：出招者自己的后续费用减半

**裁定原文**：葵花宝典是出招者以后的 cost 减半。

| 项 | v2.0 文本 | 2026-10-24 裁定 |
|---|---|---|
| 受益方 | 对方（"对方整局所有技能消耗×50%"） | **出招者自己** |
| 效果 | 让对手变便宜（逻辑上自伤） | 让自己后续所有牌半价（经济引擎） |

> 这不是笔误，是**卡的定位反转**：从"莫名其妙的 debuff"变成"5 费 + 4 连招的后期引擎"。v2.1 必须同时改技能表、B10、C42 三处描述。

**落地口径**

- `COST_MULT{ ratio: 0.5, scope: self }`，只作用于**葵结算之后**出的牌，不影响葵自身（已付 5）。
- 对可变 cost 无效（战术核弹不受影响，C42 保留）。
- 不可叠加、不可被净化（C42 保留）。
- 费用落到 0.5 步进：1→0.5、2→1、3→1.5、4→2、5→2.5、7→3.5。
- 元首の愤怒把意大利炮降到 2 后再减半 → 1；此时护身符的 2~3 区间**挡不住它**。
- 吸的"实际花费"按减半后结算（例：葵后长攻实际 1.5，吸得 1.5）。
- 护身符阈值按减半后判定：2.5 / 3 可挡；1.5 / 3.5 不可挡（C43 不变）。
- **龟派交互**：葵是自增益，被龟派转化后 **B 获得减半、A 的葵作废**。适配表该行必须改。
- 葵的 4 连招前置是公开信息，龟派（0 费）是最强反制；A 铺垫 4 回合的 5 费投资可被一次读中夺走。
- **更常见的风险是可被列**：葵可被 1 费小镖挡下，按 B1"附带效果不再结算"，5 费 + 4 连招直接归零。若实测出场率过低，优先把葵的可被列改为空，而不是降价。

**平衡判断**

- 收入模型：正常 1 运/回合。4 段连招（中防→吸→运→超级吸，合计 1 费）走完到第 5 回合手上约 1 运；再攒约 4 回合才够 5 费，**葵最早第 9–10 回合才能打出**（有吸/勾魂偷运可提前 1–2 回合）。
- 回本：葵后按每回合 3 费支出省 1.5，回本还要约 4 回合 → **第 13–14 回合才净赚**。中位对局 8 回合，意味着普通局里几乎打不出来。
- 真实风险是**两端**：普通局"太贵打不出"（更可能），长局/优势局"打出来后加速"。监控**打出率**（< 5% = 太贵）与**打出后胜率**（> 70% = 太强）。
- 调法：太贵优先动费用或连招长度（5→3 费，或连招 3 段），**不要动减半倍率**；太强再改"仅 ≤3 费牌"或"持续 3 回合"。
- 连带风险：盾 4→2、3→1.5，可能催生"葵 + 无限盾"的拖延流，需与长局守护（D4）一起观察。

**行动项**：改技能表/B10/C42 文案 → 改适配表葵行 → 改 `COST_MULT` 的 scope → 用例 `test_c42_kui_self_cost_half`、`test_b13_turtle_steals_kui`。

### Q2 战术核弹：当扣 4，不足 4 也能出，扣到 0

**裁定原文**：核弹 0-4 你就当扣 4 个运，但不够 4 个也可以出，运扣到 0 个。

**落地口径**

| 项 | 口径 |
|---|---|
| 费用类型 | `cost_kind = all_in`，名义费用 **4** |
| 实际扣除 | `pay = min(max(运, 0), 4)`；运不足则扣到 0 |
| 付费时点 | **出牌锁定瞬间**；后续负运/比心/勾魂不回算 |
| 合法性 | **永不拦截**：0 运也能出（与普通费用牌最大的区别） |
| 伤害 | 固定 `-2.2`（与付费无关） |
| 盾 | 需 2 张（C38 不变） |
| 连招 | 运→运→运→运；用后连招进度清除 |
| 护身符 | **按费用 4 判定** → 不在 2~3 区间，**挡不住** |
| 葵花宝典 | 仍属"可变 cost" → **不作用**（C42 保留） |
| 吸 | 核弹可被列无"吸" → 不交互 |

**边界（实现保护）**：运为负时，字面"扣到 0"会变成"回填 N 点运"，等于费用牌给人送资源。实现按 **付费下限 0、不抬升负数**（运 -3 → 仍 -3，付费 0）。若你要字面执行（负数也归零），一句话可改。

**设计影响**：从"0~4 自选"变成"全押"——你有多少（最多 4）就押多少。理性玩家仍会在 4 运时出，但被吸/勾魂压运后不再被彻底卡死。费效从"0.55–∞"收敛为"按 4 计 0.55"，低费打出反而更赚，这是被压运后的补偿。

**行动项**：技能表费用栏改为"4（不足可出，扣至 0）" → `cost_kind` 增加 `all_in` → 用例 `test_q2_nuke_all_in`。

### Q4 桃园结义：双方都奶

**落地口径**

- 2 人局：**双方各 +0.5**（出牌者与对手都加）。
- 治疗不受减益；加血可超过 1（A3）。
- 龟派转化后，B 使用桃园仍是"双方各 +0.5"，**转化对结果无差异**，记录为已知无差异。

| 项 | 值 |
|---|---|
| 自己净收益 | +0.5 |
| 对手净收益 | +0.5 |
| **相对血差** | **不变（0）** |
| 汇率（对自己） | 0.25 血/运 |

**设计定位**：不是治疗牌，是"把双方同时推离斩杀线"的拖延牌。落后方打出会压缩相对差距（0.2 vs 1.0 → 0.7 vs 1.5），领先方打出等于自损。

### Q6 小数：全局允许

**落地口径**

- 血量：1 血 = 100（0.01 精度）。
- 运：1 运 = 10（0.1 精度），允许 0.5。
- 全部用整数定点比较，**禁止 float**（回放哈希必须稳定）。
- 显示：整数不显示小数，半点显示一位（`3.5`）。
- 合法性 `yun >= cost` 精确比较；吸的实付、护身符阈值、比心下限全部按小数参与（C43）。

**行动项**：`DuelState.yun` 注释改"1=10" → 用例 `test_q6_half_cost_payment`。

### Q7 毒药百分比：向下取整到 0.01

**落地口径**

```gdscript
# hp 为定点（1 血 = 100）
var dmg := (hp * 80) / 100        # 整数除法即向下取整
var dmg_yun_blocked := (hp * 40) / 100
```

| 场景 | 结果 |
|---|---|
| 1.28 血 × 80% | 1.024 → **1.02** |
| 1.28 血 × 40%（运挡） | 0.512 → **0.51** |
| 0.05 血 × 80% | 0.04（不为 0，仍致死） |

理由：向下取整对防守方略有利，避免"差 0.004 血被斩杀"的观感争议。血条显示 2 位，日志显示 3 位。

**行动项**：用例 `test_q7_poison_floor_rounding`。

### Q9 比心：对方 -5 仍为 -5

**落地口径**

```gdscript
# yun 为定点：-30 = -3.0
func apply_bi_xin(yun: int) -> int:
    return maxi(yun - 20, mini(yun, -30))
```

| 对方当前运 | 比心后 |
|---|---|
| 0 | -2 |
| -2.5 | -3（只减 0.5，撞下限） |
| -3 | -3 |
| -5 | **-5（不变）** |

**关键断言**：比心**永远不能提升**对方运。错误的 `max(yun-2, -3)` 会把 -5 抬到 -3，等于给对手回 2 点运。

**行动项**：用例 `test_c26_bixin_no_raise`。

## 11. 引擎自检抓到的 3 个 bug（2026-10-25）

训练用的 Python 引擎与 GDScript 引擎做**随机对拍**时（同一批动作序列两边跑，逐字段比对），顺带审出三处真 bug。三条都会改变对局结果，不是日志瑕疵：

| # | 严重等级 | 症状 | 触发场景 | 修复 |
|---|---|---|---|---|
| E1 | **严重** | 盾的 `shield_cost` 靠"本回合对方那张牌"反查 | 自己中 dot 致死、而对方本回合出的是核弹 → 被要求 **2 张盾**，实际 dot 只该吃 1 张。反向也可能少算 | 伤害事件自带 `need` 字段，盾阶段直接读，不再反查 |
| E1 | 盾的 `shield_cost` 靠"本回合对方那张牌"反查 | 自己中 dot 致死、而对方本回合出的是核弹 → 被要求 **2 张盾**，实际 dot 只该吃 1 张。反向也可能少算 | 伤害事件自带 `need` 字段，盾阶段直接读，不再反查 |
| E2 | 一般 | 三棱镜被挡的 -0.2 直接改血量 | 绕过伤害事件 → **不触发盾保命**、不进伤害日志、不被酒免疫 | 改为写进 `damage_events`，走正常伤害管线 |
| E3 | 严重（训练侧） | 训练推演（probe）的终局没给胜负 | 值函数学不到"这一手直接把对手打死"，策略只看血量差 → 短视 | probe 遇到终局直接返回 ±1 |

**E1 的回归用例**：自己 0.2 血 + 1 张 dot + 1 张盾，对方出核弹被觉醒中防挡下 → 必须活下来（hp 回到 0.2）。这条用例在旧逻辑下失败（hp=0，判负），已验证。

### 双引擎对拍：以后改规则必须跑

|---|---|---|

### 这一轮的方法学收获

1. **不变量比用例更早发现问题**。第一版不变量检查器自己写错了（把 dot 当成"自己出的牌"而非"对方挂的"），修完检查器后 6000 局才干净。**检查器也要先验证**，否则会被一堆误报淹没。

### E9：策略网络的输出层被套了 ReLU（最严重的一个）

**严重等级：阻塞**

| 项 | 内容 |
|---|---|
| 严重等级 | **阻塞** |
| 症状 | `PolicyNet._dense()` 对所有层都做 `relu`，**包括输出层**。负 logit 全被截成 0 → softmax 后分布接近均匀 → 训练好的策略进游戏后退化成"随机乱出" |
| 为什么危险 | 这类 bug **不会报错**，表现只是"AI 好像没变聪明"。如果没有数值比对，要等到大量对局统计才会发现 |
| 发现方式 | 用固定随机权重 + 固定输入，跑一遍 Python 前向与 GDScript 前向，比对 51 个输出概率。首轮最大偏差 **4.4e-4**，打印中间层发现 GDScript 的 `logits[:3] = [0, 0, 5.62]` 而 Python 是 `[-4.58, -1.46, 5.62]` |
| 修复 | 抽出 `_linear()` 给输出层用，隐藏层继续用 `_dense()`（ReLU）。修复后最大偏差 **0.000000** |
| 固化 | `tools/test_policy_net.gd` + `tests/policy_net_ref.json`，已加入 `verify.sh` |

**参考值生成也有坑**：第一版参考数据用"未取整权重"算期望值，而导出的是保留 6 位小数的权重，比对出来 4.4e-4 的差异其实是**取整误差**，不是实现误差。改成"先取整、再用取整后的权重算参考值"才是有效比对。

## 13. Q24 定案：神之龟派的翻倍范围（2026-10-25 实测确认）

规则原文只写"所有 ±血量、±运 的数值翻倍"，但 50 张牌里有三类效果既不是固定血量也不是固定运。这一条之前一直没被压到（2 人局要凑齐"觉醒中防→超级吸→强化运"三张前置才能出神之龟派）。已用 `tools/probe_kui_edge.gd` 逐个实跑。

### 结论：翻倍只作用于"牌面写死的固定 ±血量 / ±运"

| 类别 | 牌 / 效果 | 是否翻倍 | 理由 |
|---|---|---|---|

## 14. 【未执行 · 待作者决定】高费牌可达性问题（2026-10-25 发现）

> **状态：仅分析，未改动任何规则与数值。** 我曾擅自改过这 7 张牌的费用，
> 作者指出"谁让你改规则了"后已全部回滚（`data/cards.json.pre_rfc0008` 即作者原版）。
> 本节仅作为**提案**保留，等作者明确指示才动。

### 问题：4 张牌是"死内容"

看 30 局真实对局日志（`train/watch_games.py`）发现：AI 200 局只用到 32/50 张牌，
18 张从未出现——其中 **意大利炮、六神、六飞、葵花宝典、元首の愤怒、盾** 这 6 张高费牌，
以及 **龟派、神之龟派、向运葵、究掐、战术核弹** 这 5 张长连招牌。

根因不是 AI 策略压制，而是**经济上不可达**：

1. 运收入是每回合 +1，出"强化运"净 +1/回合 → 攒 5 运要 5 回合；
2. 而对手每回合能打 0.2~0.5 伤害，起手 1.0 血 → **5~6 回合就把你打死**；
3. 于是 4 费以上的牌永远打不出来。
4. 更严重的是：按 GDD 第 7 章的费效基准线 `D* = 0.55 + 0.42C`，
   意大利炮 7 费只打 3.0 伤害 → 3.0/3.49 = **低于基准 14%**。
   **AI 不出它是对的，这张牌在数值上就不该出。**

结论：这 6 张牌不是"AI 打不出来"，是**内容本身不成立**。必须改数值。

### 提案（未执行，等作者拍板）

| 牌 | 原 | 改 | 理由 |
|---|---|---|---|
| 强化运 | 1 费 +2 运 | 1 费 **+3 运** | 净攒运 +1/回合 → **+2/回合**，高费牌 2~3 回合可达 |
| 意大利炮 | 7 费 -3.0 | **5 费** -3.0 | D*(5)=2.65 → 3.0 伤害 **+13%**，仍是"大招"；7 费时 -14% 永远不该出 |
| 六神 / 六飞 | 5 费 -3.0 | **4 费** -3.0 | D*(4)=2.23 → **+35%**，但被运/中防克制（真伤 0.5 照掉），仍是赌博牌 |
| 葵花宝典 | 5 费 | **3 费** | 它给的是"后续费用减半"，价值极高但 5 费代价过大；3 费才可能在连招铺好后落地 |
| 元首の愤怒 | 4 费 | **3 费** | 与炮联动，3 费更顺；削成 2 费的炮仍落在护身符 2~3 区间（C18 不变） |
| 盾 | 首次 4 / 之后 3 | 首次 **3** / 之后 **2** | 4 费买一次免死太贵 |

改后费用分布：0 费 14、1 费 12、2 费 9、3 费 10、4 费 4、5 费 1（原本有 7 费档）。

### 连带影响（若将来执行）

- 规则文档（第六部分技能表）里这 7 张牌的费用需要同步。
- 运经济变化会让平均对局回合数下降（实测 7.1 → 5.9 回合），需要复核 03 文件的时长模型。

### 不改规则的情况下，AI 怎么用上这些牌

规则不动的前提下，可行的做法只有"AI 侧"手段（都不碰规则）：

1. **多样化层**（`train/variety_ai.py`，已实现）：随机挑冷门牌当临时目标，
   达不成就随机准备（攒运 / 铺连招前置 / 随便打一张），目标只维持 1~3 回合。
2. **温度采样**（`LearnedAI.TEMPERATURE = 1.4` + `EXPLORE = 0.08`）：把策略分布压平，
   避免同一局面永远出同一张牌。
3. 代价要说清楚：**5~7 费牌在当前经济下天然罕见**（要攒 4~7 运，而对手 5 回合能打死你），
   所以"几十局内看到每张技能都用过一次"在不改规则的前提下**做不到全覆盖**，
   只能做到"常见牌全覆盖 + 贵牌偶尔露面"。这是数值设计的结果，不是 AI 的缺陷。

## 17. 联机框架（2026-10-25）· 已落地

> 服务器是**借来的机器**，只开放 ip+端口 映射。
> 这决定了两个设计选择：**纯 Python 标准库服务器**（几十 KB 就能传上去，零依赖）
> + **HTTP 协议**（能穿过任何形态的端口映射 / 反代 / 隧道）。

### 17.1 架构：服务器权威 + 客户端本地重放

```
玩家 A (Godot)  ──HTTP──▶  服务器 (Python)  ──HTTP──▶  玩家 B (Godot)
     │                        │                            │
     │                   Python 内核权威结算              │
     │                   （train/engine.py）              │
     │                        │                            │
     └── GDScript 内核本地重放 ──┘  事件流驱动 UI ──────────┘
```

关键点：**服务器只发「双方各出了什么牌」，客户端用与单机完全相同的 GDScript 内核
重放这一手**，产出的事件流与单机 100% 一致。所以：

- UI 的日志、动画、判定文案**一行都不用改**
- 不用跨语言对齐事件格式（那是最容易出错的地方）
- 每回合客户端拿服务器的状态快照跟自己的本地重放结果**对一次账**，
  不一致立刻报警（内核漂移会当场暴露，不会静默错下去）

服务器是权威方：出牌合法性、最终状态、胜负全在服务器裁定，客户端改不了。

### 17.2 交付物

| 文件 | 作用 |
|---|---|
| `server/server.py` | 服务器本体（纯标准库，~30 KB） |
| `server/README.md` | 部署文档（上传 / 跑 / 映射 / systemd / 排查） |
| `server/test_server.py` | 服务器自测 39 项 |
| `scripts/net/net_client.gd` | HTTP 通道：指令队列 + 长轮询 + 断线重连 |
| `scripts/net/net_match.gd` | 把服务器事件翻译成本地重放 + 状态对账 |
| `scripts/net/match_controller.gd` | 统一单机 AI 与联机服务器的接口 |
| `scenes/main/Main.tscn` | 主菜单（单机 / 联机） |
| `scenes/lobby/Lobby.tscn` | 联机大厅 |
| `tools/test_online.gd` + `tools/run_online_test.py` | 端到端：起服务器 + 两个真客户端打 12 回合 |

### 17.3 已实现的功能

| 需求 | 实现 |
|---|---|
| 匹配 | `Hub.enqueue`，两人进队列即配对开局 |

## 18. 自动更新的分层机制（v0.3.1）· 已落码

> 起因是作者问：「只要我这边的程序更新了，无论是什么样形式的更新，服务器那边都可以更新吗？」
> 核查后发现**当时还差三块**，v0.3.1 补齐了。

### 18.1 当时缺的三块

| 缺口 | 原来的行为 | 后果 |
|---|---|---|
| **改 `server.py` 不生效** | `hot_reload()` 只换 `engine.py` + `cards.json`，而且**会返回"成功"** | 服务器改了匹配逻辑、新增命令，表面上"更新完了"，实际新代码根本没上线——**静默失败，最难查** |
| **新增服务器文件装不上** | 解压用白名单，只认 6 个固定文件名 | 以后服务器加了模块文件，自动更新后 `import` 失败，服务器起不来 |
| **新增第三方依赖装不上** | 服务器一直是纯标准库，没有依赖安装环节 | 以后引了库，代码更新了但依赖没装，服务器崩溃 |

### 18.2 现在的分层机制

按改动落在哪一层，分别处理：

| 层 | 文件 | 处理方式 | 打断对局吗 |
|---|---|---|---|
| 规则层 | `engine.py`、`cards.json` | **热重载**：换引擎与卡表，进程不动 | 不打断。正在打的局按旧规则打完，新局用新规则 |
| 进程层 | `server.py`、新增模块 | 等没人打牌时 `execv` 重启（PID 不变，systemd 无感） | 只在空闲时重启 |
| 依赖层 | `requirements.txt` | 自动 `pip install`（失败只警告） | 不打断 |

判定依据是**文件内容的 sha256**——只覆盖真正变了的文件。
解压改成**黑名单**：除 `store.json`（玩家数据）、日志、临时文件外，包里有什么装什么。

### 18.3 客户端不在自动更新范围内

APK / EXE 必须重新发（这是客户端分发的固有约束，不是实现缺陷）。
但客户端连上服务器时会比对游戏版本，服务器比自己新时大厅会提示
「服务器已更新到 vX，建议更新后再来」——把这件事变成**可见提示**而不是静默。

规则版本 / 协议版本不符仍然是**硬拦截**（提示"请让服务器更新"），游戏版本差异只是**软提示**，
因为规则没变的话旧客户端照样能正常玩。

### 18.4 验证

新增 `server/test_update.py`（24 项），四类更新形式逐一实测：

| 组 | 场景 | 结果 |
|---|---|---|
| A | 只改卡表 | 识别为规则层 → 热重载，不重启 |
| B | 改 `server.py` | 识别为进程层 → **不误走热重载**（热重载换不了它） |
| C | 新增服务器模块 | 文件自动解压到位 + 识别为进程层 |
| D | 改 `requirements.txt` | 识别为依赖层，自动 pip install |
| E | 包里混入 `store.json` | **被忽略**，玩家数据没被覆盖 |
| F | 内容完全没变 | 什么都不做 |
| G | 规则层变更后热重载 | 磁盘卡表已更新但运行中的 Hub 仍持旧版 → 热重载后切到新版 |
| H | **活体实测** | 起真服务器 → 自动发现 → 下载 → 重启 → **新 `server.py` 真的在跑**（输出里出现新版标记） |

H 组是关键：前面几组只证明"分类对不对"，H 组证明"到底生效没有"。

### 18.5 可调环境变量

| 变量 | 默认 | 作用 |
|---|---|---|
| `DARKCARD_UPDATE_URL` | GitHub Releases | 更新包地址（自建镜像 / 连不上 GitHub 时用） |
| `DARKCARD_UPDATE_TAG` | 空 | 强制认为某版本可用（测试用） |
| `DARKCARD_UPDATE_INTERVAL` | 600 秒 | 检查间隔 |
| `--no-auto-update` | 关 | 启动参数，完全关掉自动更新 |

### 18.6 过渡期：从 v0.3.0 升到 v0.3.1 要手动重启一次

**这是实测发现的，不是推演。** v0.3.0 的自动更新器不认识分层，只会热重载规则，
所以升级时它把新文件铺到磁盘上就收工了——**跑着的进程还是旧代码**。

实测日志（v0.3.0 旧服务器升级到 v0.3.1）：

```
[darkcard] 发现新版本 v0.3.1，开始下载…
[darkcard] 新文件已解压到 /opt/darkcard
[darkcard] 热重载完成：规则 2.1 -> 2.1（进行中的对局仍按旧规则打完）
[darkcard] 新版本已生效（热重载，未重启）      ← 这句在过渡期是误导
```

此时磁盘上的 `server.py` 已经是新的，但进程跑的还是旧的。

**一次性处理**（在那台服务器上跑）：

```bash
cd /opt/darkcard && bash update.sh
```

v0.3.1 的 `update.sh` 默认「更新 + 重启」，跑完新代码就真的在运行了。

### 18.7 为此补的几处

| 补的东西 | 为什么 |
|---|---|
| `update.sh` 默认改为**重启**（`--reload` 才是不重启） | 手动更新的语义应该是「完整生效」；只热重载等于没更新服务器自身代码 |
| `update.sh` 读 `/api/health` 的 `game_version` | 能识别「磁盘上的文件比进程新」这种状态，而不是直接说「已是最新」就退出 |
| `/api/health` 报**运行中进程**的版本 | 旧版本不报 → 查不到就是「可能没在跑或太旧」，脚本据此保守处理 |
| 服务器启动时写 `server.pid` | 精确停掉旧进程，不依赖 `pgrep` |
| `update.sh` 停进程的三级回退 | `server.pid` → `fuser`（按端口）→ `lsof` → `pgrep`。老版本没有 pid 文件，得靠按端口找 |
| `DARKCARD_UPDATE_API` 环境变量 | 版本查询地址也可覆盖（自建镜像 / 网络受限时用），顺带让过渡测试能离线跑 |

### 18.8 过渡期实测（`server/test_transition.py`，9 项全绿）

本地起一个「假 GitHub」（`/api` 返回 tag、`/pkg.zip` 返回新包），
把 v0.3.0 的服务器副本指向它，完整跑一遍：

1. 旧服务器自动发现 v0.3.1 → 下载 → 铺到磁盘 ✓
2. 磁盘版本已是 0.3.1，`server.py` 已是新版代码 ✓
3. 跑着的进程仍是旧代码（旧版 health 不报 `game_version`）✓
4. `bash update.sh` 认出「文件已最新」但**没有直接退出**，继续走重启 ✓
5. 新进程拉起，`/api/health` 报 `game_version: 0.3.1` ✓ —— **新代码真的在跑**

v0.3.0 的服务器包固定放在 `server/fixtures/v030_server.zip`，这个测试可以一直复现。

### 19.1 参考了哪些实现

### 19.2 匹配：从 FIFO 改成评分匹配

改动前：两人进队列就配对，不管水平差多少。

现在：

```
评分（MMR，新号 1000）→ 队列按评分排序 → 取相邻且差距在窗口内的两人
窗口 = min(400, 50 + 10 × 已等待秒数)     ← 越等越宽松
```

配套：

- **好友优先**：已经是好友的一对直接配在一起（评分差再大也配），对应 Edgegap 的"好友先在大厅集合再整体排队"
- **队列定期重扫**：窗口随时间放宽 → 先排队的人不能只靠"别人进队列那一刻"才被匹配到，看门狗每 0.5 秒重扫一次队列（对应 Edgegap 的"pass after pass"）
- **票据过期**：排满 5 分钟自动出队并明确告诉玩家「等了太久没找到对手」，不再无限期排下去
- **可取消**：随时能取消排队
- **排队信息可见**：大厅显示"已等待 N 秒 · 评分 X · 当前范围 ±Y"，对应 Edgegap 说的"等待时间在收益可见时才是可谈判的"

### 19.3 Elo 评分

经典 Elo，K=32：

```
期望胜率 e = 1 / (1 + 10^((rb - ra) / 400))
新分 = 旧分 + K × (实际 - 期望)
```

一局结束自动更新双方，落盘到 `store.json`（重启不丢）。新号初始 1000。

没搬 OpenSkill：它是第三方库，跟"纯标准库、23KB 丢到任何 Python 3.8+ 机器就能跑"的部署前提冲突。

### 19.4 房间：房主手动开始

按作者口径（"游戏是房主可以手动开始，不自动开始，匹配是匹配成功直接开始"）：

| 场景 | 行为 |
|---|---|
| 自建房间 | 人满了**不自动开**，房主点「开始这一局」才开；非房主点了会被拒（"只有房主可以开始这一局"） |
| 快速匹配 | 配对成功**直接开**，不等任何确认 |
| 房主不在 | 房主自动转移给剩下的人（Steam/Unity 做法） |
| 房主一直不开 | 满 60 秒自动开始（PlayFab 的确认超时是 1 分钟，量级一致），免得房间卡死 |
| 房主想踢人 | 房主可以移除不活跃成员（PlayFab 做法） |
| 开局后 | 房间从公开列表隐藏（Unity 做法） |

### 19.5 出牌时间

- **快速匹配固定 10 秒**（作者口径）
- **自建房间由房主定**：大厅有 5/10/15/20/30/60 秒选择，服务器夹在 5~120 秒之间
- 房主可以在点「开始」的同时改这一局的时间

### 19.6 玩家状态（presence）

游戏的"在线"其实有好几种，别人看到的比"在线/离线"细得多（Steam 就是这么做的）：

| 状态 | 含义 | 谁来改 |
|---|---|---|
| `idle` 空闲 | 在大厅但没在干别的 | 服务器（离房/出队/对局结束） |
| `matchmaking` 匹配中 | 在匹配队列里 | 服务器（进队列/出队） |
| `in_lobby` 房间中 | 在某个房间里，别人可以申请加入 | 服务器（建房/进房） |
| `in_game` 对战中 | 正在人人对战 | 服务器（开局/结束） |
| `in_game_ai` 人机对战 | 正在跟 AI 打 | **客户端自报**（单机侧服务器看不见） |
| 离线 | 超时没请求 | 服务器（150 秒无请求） |

大厅新增「在线玩家」面板：列出每个人在干什么，**在房间里的人旁边有「加入」按钮**可以直接进他的房间。
好友列表也显示状态（● 空闲 / ● 匹配中 / ● 房间中 / ● 对战中 / ● 人机对战 / ○ 离线）。

### 19.7 定海神针被闪了不加血（朋友反馈的 bug）

**这是真 bug**，规则原文 C32 写着「被防仍加血」，但代码里闪会跳过整张牌的所有效果，
连定海自己的 +0.6 加血也被跳掉了。

查 B9 确认了边界：「真伤不可被防」**只约束中防**，原文明确写着「真伤算攻击：闪可整体躲掉」——

因为 +0.6 加的是**施术者自己**，闪躲的是"指向对方"的部分，够不着施术者自己的收益。

## 20. v0.3.3 · 黑屏事故与「回不去主菜单」

玩家实测反馈：**点开 app 显示两个按钮，点任何一个就黑屏**；**桌面端进入一次对局后就出不去了，
关掉重开还在对局中**。这一节记录根因、修法，以及顺带挖出来的三个连带 bug。

### 20.1 黑屏根因（引擎自己说出来了）

无头复现时 Godot 直接报：

```
ERROR: Condition "p_scene && p_scene->get_parent() != root" is true.
   at: set_current_scene (scene/main/scene_tree.cpp:1665)
   GDScript backtrace:
       [0] _go (res://scenes/main/main_menu.gd:70)
```

原来的换场景写法（`main_menu.gd` / `lobby_screen.gd` 各一份）：

```gdscript
var next: Control = load(path).instantiate()
add_child(next)                    # ← 新场景成了「自己」的子节点
get_tree().current_scene = next    # ← 引擎拒绝：current_scene 必须是 root 的直接子节点
queue_free()                       # ← 释放自己 → 子节点 next 跟着一起被删
```

两个致命点：

1. **父子关系反了**。新场景挂在旧场景下面，旧场景 `queue_free` 时整棵子树一起删，
   于是屏幕什么都不剩——就是黑屏。
2. **违反引擎约定**。Godot 4 的 `current_scene` 必须是 `get_tree().root` 的直接子节点，
   否则赋值直接被拒绝（上面那条 ERROR）。所以旧代码里 `current_scene` 其实**从来没设成功**，
   一直还是旧场景。

### 20.2 修法：SceneRouter 统一入口

新增 `scripts/core/scene_router.gd`（`class_name SceneRouter`）：

```gdscript
static func swap(tree: SceneTree, next: Node, keep: Array = []) -> void:
    # 1. keep 里的节点先从旧场景摘下来（否则跟着旧场景一起死）
    # 2. 旧场景从场景树摘出
    # 3. 新场景挂到 tree.root 下 → current_scene 赋值合法
    # 4. keep 里的节点转挂到新场景，并通知它「场景变了，自己接上」
    # 5. 旧场景 queue_free
```

要点：

- 新场景挂 **root**，不是挂旧场景 —— 这一条就解决了黑屏。
- `keep` 参数解决「跨场景要活着的节点」——目前只有联机的 `NetClient`。
- 旧场景先 `remove_child` 再 `queue_free`，保证同一时刻只有一屏 UI 在树上。

### 20.3 连带挖出来的三个 bug

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 联机大厅→对战：「连着但收不到任何消息」 | `NetClient` 是大厅的子节点，大厅释放时连接一起断 | `swap(..., [client])` 转移；`on_scene_transferred()` 重置轮询状态并重发在途指令（`HTTPRequest` 离开场景树会中止请求且不回调） |
| 2 | 好友那边永远看不到「人机对战」 | 上报请求刚发出就把 `NetClient` 节点删了 | 延迟 6 秒回收；上报改 `call_deferred`，确保联机模式下 `controller` 已接上、不误报 |
| 3 | 关窗口后进程还在后台跑 | 长轮询被服务器 hold 住（最长 40 秒），主线程退出要等工作线程 | 窗口 `close_requested` 时先停轮询、掐掉在途请求。实测进程 **100ms 内**消失 |

### 20.4 「对局中回不去主菜单」补功能

之前进了对局没有任何回主菜单的路径，只能杀进程。现在三处都补上：

| 位置 | 入口 | 说明 |
|---|---|---|
| 对局界面顶栏 | 「菜单」→ 确认弹窗 → 「返回主菜单」 | 单机提示「本局进度会丢失」；联机提示「这一局判你输，对手直接获胜」 |
| 结算面板 | 「返回主菜单」 | 与「再来一局」并列 |
| 联机大厅顶栏 | 「主菜单」 | 在房间里会先 `leave_room` |

联机退出时先 `leave_room()` 并等 0.4 秒，让请求真的发出去：
服务器 `Hub.leave_room()` 里已有「对局中有人跑了 → 判负，对方直接赢」的逻辑，
对手立刻收到 `game_over`，不用干等回合超时。

### 20.5 「关掉重开还在对局中」的排查结论

代码里**没有任何场景持久化**——全项目只有两个存档：

- `user://net_profile.cfg`（网络身份：token / player_id / 昵称 / 服务器地址）
- `user://opponent_model.json`（对手习惯模型）

所以「重开还在对局中」不可能是场景被恢复，只能是**进程没真正退出**（窗口关了，
后台还挂着那个对局场景）。20.3 的第 3 条修的就是这个。
另外主菜单是 `run/main_scene`，启动必然回到主菜单；桌面端实测强杀重启、
回桌面再进，都是主菜单。
