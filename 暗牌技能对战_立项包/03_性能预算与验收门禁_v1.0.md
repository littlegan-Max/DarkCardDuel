## 0. 为什么卡牌游戏也要做性能预算

这类游戏的性能问题不在"画面太重"，而在三处：

1. **UI 节点太多**：50 张牌 × 每张 5 个 CanvasItem = 250 绘制项，滚动时每帧重排。
2. **结算瞬间尖峰**：一次翻开要跑完 10 步结算 + 演出 + 日志刷新，容易在翻开那一帧掉到 80ms。
3. **内存悄悄涨**：每局新建卡牌节点/Tween/信号，十局后 OOM。

所以预算的重点是**节点数、尖峰帧、内存斜率**，不是三角形数。

---

## 1. 帧预算

### 1.1 60fps（B/C 档）

| 阶段 | 预算 | 说明 |
|---|---|---|
| 逻辑（TurnDirector/动画驱动） | 2.0ms | 每帧只做插值与状态推进，规则只在翻牌时跑一次 |
| UI 布局与文本 | 3.0ms | 血/运数字用 `Label`，避免每帧 `invalidate` |
| 绘制提交（CPU） | 4.0ms | 绘制项 ≤ 80 |
| GPU | 5.0ms | 填充率为主，overdraw ≤ 2.5× |
| 余量 | 2.6ms | 留给系统抖动与通知栏弹出 |
| **合计** | **16.6ms** | |

### 1.2 30fps（A 档低端）

| 阶段 | 预算 |
|---|---|
| 逻辑 | 3.0ms |
| UI | 6.0ms |
| 绘制提交 | 8.0ms |
| GPU | 12.0ms |
| 余量 | 4.3ms |
| **合计** | **33.3ms** |

### 1.3 尖峰规则

| 事件 | 允许峰值 | 处理 |
|---|---|---|
| 翻开瞬间 | ≤ 50ms（不超过 2 帧） | 演出资源全部预加载，事件流预分配 |
| 一次性结算（10 步） | 总 CPU ≤ 8ms（不含演出等待） | 纯计算，无 IO、无 `load()` |
| 首帧进入战斗 | ≤ 800ms（含淡入） | 异步加载 + 转场遮罩 |
| GC 抖动 | 单帧 ≤ 2ms | 避免每回合新建大数组（复用 buffer） |

> 规则：**任何超过 50ms 的单帧都算缺陷**，必须定位到具体函数，不接受"卡一下正常"。

## 2. 内存预算

| 项 | A 档 | B 档 | C 档 |
|---|---|---|---|
| 引擎基线 | 60MB | 60MB | 70MB |
| 纹理 | 80MB | 100MB | 120MB |
| 音频 | 8MB | 8MB | 10MB |
| 字体 | 3MB | 4MB | 4MB |
| 脚本/数据 | 15MB | 15MB | 15MB |
| 运行时余量 | 40MB | 60MB | 80MB |
| **PSS 上限** | **250MB** | **300MB** | **350MB** |

**内存斜率（泄漏判定）**：连续 10 局对局后，PSS 增长 ≤ 15MB；`Performance.get_monitor(OBJECT_COUNT)` 增长 ≤ 100；`ORPHAN_NODE_COUNT` 必须为 0。

---

## 3. 包体预算

| 项 | 预算 | 做法 |
|---|---|---|
| AAB 下载体积 | ≤ 150MB（目标 100MB） | — |
| 首包 | ≤ 60MB | 卡面按章节分包（`asset packs` 可选） |
| 卡面 | 512×716 → ASTC 6×6，2048² 图集 7 张 | 每图集 8 张牌（4×2） |
| 纹理总显存 | ≤ 25MB | ASTC 6×6 ≈ 3.56 bit/px |
| BGM | 2 首 OGG ≤ 3MB | 128kbps |
| SFX | ≤ 60 个 ≤ 5MB | OGG/ADPCM，短音效 |
| 字体 | ≤ 3MB | 中文子集化（只保留游戏用字 + 常用 3500 字） |
| 规则文本 | JSON ≤ 300KB | 不打进贴图 |

> 卡面若改成"插画级"（1024×1432），纹理预算要翻 4 倍，包体会破 200MB。**美术风格必须先定档再排期**（见 01 文件 R9/待补 5）。

## 4. 加载预算

| 场景 | 目标 | 手段 |
|---|---|---|
| 冷启动 → 主菜单 | ≤ 3.5s | 启动只加载 UI 与本地配置，卡面延迟 |
| 主菜单 → 战斗 | ≤ 1.2s | 卡面图集异步 + 转场遮罩 |
| 战斗内换回合 | 0 加载 | 全部资源常驻 |
| 结算页 | ≤ 300ms | 复用战斗场景，不切场景 |
| 规则详情页首次打开 | ≤ 200ms | 文本预解析 |

## 5. 节点与绘制预算

| 对象 | 上限 | 现状设计 |
|---|---|---|
| Battle 场景节点 | 220（峰值 260） | 见 02 文件 3.2 |
| 卡池视图节点 | 12（复用池） | 不随卡数增长 |
| 单帧绘制项 | 80（峰值 120） | 卡面图集 + 9-patch |
| 同屏 CanvasLayer | ≤ 4 | Board / Overlay / Log / Fade |
| 材质（Material）数量 | ≤ 6 | 翻开/碎裂/描边/遮罩共用 |
| Shader 变体 | ≤ 10 | 避免首帧编译尖峰 |
| Tween 同时存活 | ≤ 20 | 统一由 `TweenPool` 管理，结束即 kill |

### 卡牌列表的虚拟化（关键设计）

```
数据层：50 条 Dictionary（常驻，~20KB）
视图层：12 个 CardChip（复用）
滚动时：计算 [first, last] 可见区间 → bind(card_id) → 更新 AtlasTexture 区域
```

**禁止**：`for card in 50: instantiate(CardChip)`。这一条如果被违反，中端机滚动会从 60fps 掉到 35fps 左右（估算，实测以阶段三报告为准）。

## 6. 资源规范

| 资源 | 规范 | 原因 |
|---|---|---|
| 卡面 | 512×716，ASTC 6×6，无 alpha 通道 | 显存与包体平衡 |
| UI 图标 | 128×128，图集合并 | 减少绘制项 |
| 9-patch | 最小 24×24，边距 8px | 任意分辨率不糊 |
| 背景 | 1080×1920，ASTC 4×4 或分块 | 全屏填充是 overdraw 主因 |
| 粒子 | ≤ 3 个 GPUParticles2D 同时 | 低端机 GPU 弱 |
| 字体 | 子集化 ttf/otf，禁用系统字体回退 | 中文全量字体 10MB+ |
| 音效 | 单声道，44.1kHz，≤ 2s | 立体声无意义且占内存 |
| BGM | OGG，循环点标注 | 避免 loop 缝隙 |

## 7. 真机测试矩阵

### 7.1 档位定义（不代表具体机型实测结论）

| 档 | 硬件定义 | 系统 | 屏幕 | 帧率目标 |
|---|---|---|---|---|
| A 低端 | 4GB RAM，Mali-G52 / Adreno 610 级 | Android 10 | 720×1600 | 30fps 稳定 |
| B 中端 | 6–8GB RAM，Adreno 730 / Mali-G77 级 | Android 12–14 | 1080×2400 | 60fps |
| C 高端 | 8GB+，SD 8 Gen1+ / A14+ | Android 15 / iOS 16+ | 1080×2400+ | 60fps + 高特效 |

> 阶段三开始时必须落实**至少 3 台真机**（每档 1 台）+ 1 台 iOS。模拟器数据不作为验收依据（GPU 行为差异大）。

### 7.2 测试脚本（每次构建跑）

| # | 用例 | 时长 | 判定 |
|---|---|---|---|
| T1 | 冷启动 → 主菜单 → 战斗 → 完整一局 → 结算 → 再来一局 | 10 分钟 | 无卡顿 > 50ms，帧率达标 |
| T2 | 连续 10 局（含长局 20 回合） | 30 分钟 | PSS 增长 ≤ 15MB，无 OOM |
| T3 | 卡池快速滑动 + 搜索 + 分类切换 100 次 | 3 分钟 | 无掉帧 > 5%，无 orphan |
| T4 | 结算演出连续播放 50 次（加速/跳过混用） | 5 分钟 | 无 Tween 泄漏，无节点增长 |
| T5 | 切后台/回前台 20 次（含回合中） | 5 分钟 | 计时正确，无状态错乱 |
| T6 | 弱网（300ms 延迟 / 5% 丢包）10 局 | 15 分钟 | 无卡死，重连成功 |
| T7 | 低电量模式 / 省电模式 | 10 分钟 | 不崩，帧率降级有提示 |

### 7.3 采集指标

```
帧时间：P50 / P95 / P99（必须有 P95，不看平均值）
绘制项：Performance.get_monitor(RENDER_TOTAL_DRAW_CALLS_IN_FRAME)
对象数：OBJECT_COUNT / ORPHAN_NODE_COUNT
内存：OS.get_static_memory_usage() + 系统 PSS
加载：每场景首帧耗时
```

**PerfHud（开发版常驻）**：帧时间曲线、绘制项、对象数、静态内存、当前场景名。发布版关闭，但保留开关（连续点击版本号 5 次）。

## 8. Godot 移动端常见坑（按踩坑概率排序）

| # | 坑 | 症状 | 对策 |
|---|---|---|---|
| 1 | `_process` 里 `get_node()` | 帧率随节点深度线性下降 | `@onready var x := $Path`，禁止字符串路径 |
| 2 | 50 个 Control 每帧重排 | 滚动时 CPU 飙高 | 虚拟化 + `custom_minimum_size`，避免每帧改 `text` |
| 3 | Tween 未 kill | 内存涨、节点释放后仍回调报错 | 统一 `TweenPool`，`node.tree_exiting` 时 kill |
| 4 | 每帧 `queue_redraw()` | GPU/CPU 双高 | 只在数据变化时重绘 |
| 5 | 中文动态字体 atlas 膨胀 | 内存涨、首次显示卡顿 | 子集化字体 + 预加载常用字 |
| 6 | 纹理未开 VRAM 压缩 | 显存翻 4 倍 | 导入预设 ASTC/ETC2，移动端统一 |
| 7 | 全屏透明叠加 | overdraw 爆炸、发热 | 背景不透明、阴影用 9-patch 不用实时模糊 |
| 8 | Shader 首次编译 | 第一次翻开卡 100ms+ | 进战斗前预热（离屏画一帧） |
| 9 | 信号未断开 | ORPHAN_NODE 增长 | `connect` 时用 `CONNECT_ONE_SHOT` 或统一在 `_exit_tree` 断开 |
| 10 | `print()` 留在发布版 | 低端机 IO 抖动 | 用 `Logger`，发布版静默 |
| 11 | 大量 `duplicate(true)` | 每回合分配新对象，GC 抖动 | 复用 buffer，只 duplicate 轻量字典 |
| 12 | 音频每帧 `play()` | 声音叠加、爆音 | 同一 SFX 加 80ms 冷却 |

## 9. 优化优先级（影响 × 成本）

| 优先级 | 动作 | 预计收益 | 成本 |
|---|---|---|---|
| P0 | 卡池虚拟化（12 节点池） | 高（滚动帧率） | 中 |
| P0 | 卡面图集合并 | 高（绘制项 250→80） | 低 |
| P0 | 结算事件流预分配 | 高（消除翻开尖峰） | 中 |
| P1 | 字体子集化 | 中（内存 -8MB，首显 -300ms） | 低 |
| P1 | TweenPool | 中（内存斜率） | 低 |
| P1 | 背景不透明化 + 去实时模糊 | 中（GPU -2ms） | 低 |
| P2 | Shader 预热 | 中（消除首翻卡顿） | 低 |
| P2 | 低端机降级（关粒子/降分辨率） | 中（保 30fps） | 中 |
| P3 | 多线程资源加载 | 低（本作加载已很短） | 高 |

> 顺序原则：**先削绘制项与节点数，再谈 Shader 优化**。卡牌游戏的瓶颈 90% 在 UI 层。

## 10. 性能门禁

### 10.1 阶段三准入（缺一不开始优化）

- [ ] 完整一局可跑通（阶段二准出）
- [ ] PerfHud 可用，能导出帧时间/绘制项/内存
- [ ] 3 档真机到位（A/B/C 各 1，含 1 台 iOS）
- [ ] 基线数据已采集（未优化版本的三档帧率/内存/包体）

### 10.2 阶段三准出（缺一不出包）

- [ ] A 档：30fps，P95 帧时间 ≤ 33ms，30 分钟无 OOM
- [ ] B/C 档：60fps，P95 ≤ 16.6ms
- [ ] 翻开峰值 ≤ 50ms，无 > 50ms 单帧
- [ ] PSS：A ≤ 250MB / B ≤ 300MB / C ≤ 350MB
- [ ] 10 局后 PSS 增长 ≤ 15MB，ORPHAN_NODE = 0
- [ ] 冷启动 ≤ 3.5s，进战斗 ≤ 1.2s
- [ ] AAB 下载 ≤ 150MB
- [ ] 崩溃率 0（测试期内），无 ANR
- [ ] 优化清单 + 优化前后对比表已出（交测试角色）

### 10.3 偏差处理流程

```
超标 → 定位（PerfHud + Godot Profiler 火焰图）
     → 归因（节点/绘制/脚本/资源/网络）
     → 出方案（削/降/换/砍）
     → 复测（同机型同用例）
     → 记入优化清单（含前后数据）
```

> **不接受**"低端机就这样"。若确实无法达标，必须给出"降级策略 + 用户可见提示"，并写进风险登记册，由设计总监决定是否调整机型基线。
